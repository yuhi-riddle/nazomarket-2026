# 共同リストのメンバーと担当者

## 目的

- 共同リストで「どのアイテムを誰が買うか」が分かる
- 人ごとに予算を持ち、それぞれが自分の担当分で予算を超えていないかを確かめられる
- 部屋の全員が、誰がいくら使う予定かを見渡せる

個人リスト（共同リストに入っていないとき）の動きと保存形式は変えない。

## 1. 用語

| 用語 | 意味 |
|---|---|
| メンバー | 部屋に登録した参加者。名前と予算を持つ |
| 担当 | アイテムを買う人。メンバーのどれか、または「未定」 |
| 自分 | この端末で選んだメンバー。部屋ごとに端末に覚える |

## 2. 共有する状態

```ts
interface SharedMember {
  id: string;              // ITEM_ID_PATTERN と同じ形式。クライアントが作る
  name: string;            // 前後の空白を除いて 1〜20 文字、制御文字なし
  budgetYen: number | null;
}

interface SharedListItem {
  id: string;
  productId: string | null;
  name: string;
  priceYen: number | null;
  quantity: number;
  purchased: boolean;
  ownerId: string | null;  // 担当。null は未定
}

interface SharedListState {
  revision: number;
  members: SharedMember[]; // 登録順
  items: SharedListItem[];
}
```

- 部屋全体の予算（`budgetYen`）はなくす。全体は合計だけを出す
- メンバーは1部屋20人まで。名前の重複は、前後の空白を除き大文字小文字を区別せずに比べて拒否する
- 名前は共有リンクを知る全員に見える。画面の登録欄にもそう書く

## 3. 操作

| 操作 | 内容 |
|---|---|
| `add-member { member: { id, name } }` | メンバーを足す。予算は null で始まる |
| `rename-member { memberId, name }` | 名前を変える |
| `remove-member { memberId }` | メンバーを外す。そのメンバーが担当のアイテムは未定に戻す |
| `set-member-budget { memberId, budgetYen }` | メンバーの予算を変える。null で予算なし |
| `set-owner { itemId, ownerId }` | 担当を変える。null で未定 |
| `add { item }` | `item.ownerId` を持つ。存在しないメンバーIDは拒否 |

- `set-budget` はなくす。共同リストのサーバーはまだ公開していないので、すでにある部屋や送信待ちの操作はない前提で、古い形は受け付けない（読み込み時の検証で弾き、送信待ちの列から外す）
- 予算と担当の変更は、部屋の誰でもできる。共有リンクを渡す相手は信頼できる身内を想定しているため
- revision と競合の扱いは今と同じ。1操作で revision を1つ進める
- 型・状態の検証・操作の検証と適用は `shared-worker/src/domain.ts` に一元化し、クライアント（`src/shared/types.ts`）はその型と検証を使う。状態の直下に `budgetYen`（部屋全体の予算）を持つ旧形式の状態や、`set-budget` は、サーバーでもクライアントでも不正な入力として拒否する
- 操作の適用時は、参照するメンバーID・アイテムIDの存在を毎回確かめる。`remove-member` のあとに古い `set-owner` が届いたときは、revision 競合として拒否され、クライアントが最新状態で確かめ直す（今の競合解決の流れのまま）

## 4. 保存（SQLite Durable Object）

- `room_meta` から `budget_yen` をなくす
- `members (id TEXT PRIMARY KEY, name TEXT NOT NULL, budget_yen INTEGER, position INTEGER NOT NULL)` を足す
- `items` に `owner_id TEXT`（NULL 可）を足す
- 公開済みの部屋はないので、移行処理は書かない。テーブルは部屋の作成時に作る
- `position` は追加時に「今の最大値＋1」。外しても詰め直さない。読み出しは `position` 順
- `remove-member` は、メンバー行の削除・担当の未定化（`UPDATE items SET owner_id = NULL WHERE owner_id = ?`）・revision の更新を、今の操作と同じ1つの同期トランザクションで行う

## 5. 端末ごとの「自分」

- `localStorage` に部屋IDごとの「自分のメンバーID」を保存する。鍵や名前は入れない
- 部屋に入って自分が未選択なら、リスト画面の上に「あなたは？」の欄を出す。既存のメンバーから選ぶか、名前を入れて新しく登録する
- 自分を選ばないままでも見て編集はできる。このときアイテムを入れると担当は未定になる
- ポーリングで受け取った状態に自分のIDがなければ、その時点で未選択に戻し、「あなたは？」の欄を出す。送信待ちの操作はそのまま送り、存在しない担当を指す操作はサーバーが拒否して競合の解決画面に出る

## 5.1 送信待ちの列

- 送信待ちの列の保存キーを1つ新しい版に上げ、古い版の列は読まずに消す。移行はしない。サーバーが未公開で、古い列が実際の利用者の端末にないため
- 新しい版の列の読み込み・不正データの扱い・再試行は今と同じ

## 6. 画面

### リスト（共同リストのとき）

- 上部の合計欄を、メンバーごとの表に置き換える

| 列 | 内容 |
|---|---|
| 名前 | 自分の行には「（自分）」を付ける |
| 担当の合計 | そのメンバーが担当するアイテムの合計 |
| 予算 | その場で直せる入力欄。空欄で予算なし |
| 残り | 予算 − 担当の合計。超えたら赤字で「N円オーバー」、予算なしは「未設定」 |

- 表の下に「未定 N件・M円」と「全体の合計」を出す
- 各アイテムの行に担当の選択欄を付ける（メンバー＋未定）。44px 以上
- 読み上げ
  - メンバー表は `<table>` にし、列見出しを `<th scope="col">`、名前のセルを `<th scope="row">` にする
  - 予算欄は「〇〇さんの予算（円）」のラベルを持つ
  - 担当欄は「〇〇（アイテム名）の担当」のラベルを持つ
  - 超過は色だけでなく「N円オーバー」の文字でも出す
- ブースごとのくくりと「地図で見る」は今のまま

### 下の帯（予算メーター）

- 自分を選んでいれば「自分の担当の合計 ／ 自分の予算」を出す。超えたら今と同じく赤字と超過額
- 自分が未選択なら「全体の合計」だけを出す

### おすすめ順

- `rankForCatalog` は、好みを読むためのアイテムと、予算から引くアイテムを別の引数で受け取る。中で予算から引くのは後者だけにし、渡した予算から二重に引かない
- 個人リストでは、どちらもリスト全体。予算はリストの予算
- 共同リストでは、好み（カテゴリ・難易度の傾向）はリスト全体から読み、予算は自分の予算、予算から引くのは自分の担当アイテムだけ。自分が未選択なら予算なしとして扱う

## 7. 個人リストとの対応（bridge と store）

- 共有状態を個人用の形に写すとき、`CartItem` は今の形のまま。写した結果に次を足す
  - `members`: メンバー一覧（送信待ちの操作を当てたあと）
  - `ownerByProductId`: 商品ID → 担当メンバーID（未定は null）。今の bridge は、商品IDがない・カタログにない・同じ商品が2行あるアイテムを含む状態を個人用の形に写さず、写せない旨を出す。写せた状態では商品IDとアイテムが1対1なので、商品IDで引ける。この前提は変えない
  - `meId`: この端末の自分（いなければ null）
- store は共同モードのとき、`items` と並べて上の3つを `shared` として持ち、`subscribe` の通知で画面に渡す。個人の保存（`serializeState`）には入れず、共同リストを抜けたら捨てる
- 共同モードの `budget` は「自分の予算」を写した読み取り専用の値にする。store の `update` で `budget` が変わっても共有操作にはせず、元に戻す。予算の変更はメンバー表から `set-member-budget` を直接送る
- メンバーの追加・名前変更・削除・予算・担当の変更は、画面から共有クライアントへ直接送る。store の `update` は通さない。送信待ちの操作は今と同じく写した結果に当たるので、押した直後から画面に出る
- 一覧で「リストに入れる」を押したときの `add` は、`ownerId` に自分を入れる
- 共有の書き込みが止まっているあいだは、メンバー表と担当欄も無効にする
- 個人リストから共同リストへコピーするときは、全部を自分の担当にする。自分が未選択なら未定

## 7.1 再描画

- ポーリングで受け取った revision と送信待ちの操作がどちらも前と同じなら、store に当てない
- メンバー表は、メンバー・担当・価格・数量のどれかが変わったときだけ計算し直す。行は作り直さず、値だけ書き換える
- 担当欄は行ごとに1つ作って使い回し、担当が変わった行だけ値を書き換える。入力中の予算欄と、フォーカスのある担当欄は上書きしない

## 8. テスト

- サーバー: 各操作の適用と revision、名前・人数・予算の検証、メンバーを外したときの担当の巻き戻し、存在しない担当の拒否、SQLite に書いて読み直したときの一致
- クライアント: 状態と操作の検証（新しい形を受け、`set-budget` と部屋の予算を拒む）、bridge の担当の対応表、自分の保存と外されたときの解除
- 計算: メンバーごとの合計・残り・未定の集計、おすすめに渡す自分の予算の残り
- 画面: headless で、メンバー登録・担当の変更・人ごとの予算と超過表示・390px と 1280px の崩れを確かめる

## 判断ログ

- 予算と担当は誰でも変えられるようにした。本人だけに絞ると「自分」の偽装対策が要るが、鍵を持つ相手は身内なので手間に見合わない
- 古い `set-budget` と部屋の予算は移行せずに捨てる。共同リストのサーバーは未公開で、移行の対象がない
- 共有の情報は AppState に混ぜず、store の別の欄に持つ。個人の保存形式を変えずに済み、共同リストを抜けたときに捨てやすい
- メンバー・予算・担当の変更は store を通さずに共有クライアントへ送る。store の差分から操作を作る今の作りは `items` だけに使う
- メンバーは20人、名前は20文字までにした。会場で一緒に回る人数と、表の1行に収まる長さから決めた
